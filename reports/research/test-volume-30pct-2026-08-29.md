# `tools/` 測試碼能不能在分數不掉下少 30%

**日期**：2026-08-29 ／ **基準 commit**：`dcc65f9` ／ **量測台**：`git clone` 的隔離副本

## 一句話的答案

**不能 —— 而擋路的不是「還沒找到方法」，是機械路徑的總量不夠。**
可動的 32 支測試檔共 3,507 實質行，目標要砍 1,052 行；實跑三輪拿到 62 行，
剩下的機械上界約 **95 行**（檔內樣板，本身還是上界）。合計約 **157 行 ——
15% 的目標、4.5% 的基數**。

⚠️ 原本估計最大的一條路（把只差字面值的 `it` 併成 `it.each`，粗估 172 行）
**實測是負的**：在格式化器把區塊收成單行之後，`it.each` 的表格自己占的行數
比省下來的多，實作一組的結果是 **+1 行**。粗估沒有把表格成本算進去。

剩下的 890 行只能從**刪測試案例**來 —— 那正是這次架的七道守衛全部在擋的事。

實跑三輪的結果：3,507 → **3,445**（−62 行，5.9% 的目標）。

## 二、⚠️ 六條「達標而什麼都沒改善」的路徑

目標是「砍體積、分數不掉」。量到六條路可以**完全達標**而測試
一點沒變強。前五條的規模都跟目標同一個數量級 —— 這是本次研究的主要產出。

|                                          | 規模                           | 封法                         |
| ---------------------------------------- | ------------------------------ | ---------------------------- |
| 1 · 子行程盲區                           | 5,864 行＝**1.7 倍目標**       | 19 支釘死                    |
| 2 · 空行＋註解                           | 占可動量 **32.8%**（目標 30%） | 主指標改實質行；另加註解護欄 |
| 3 · **覆蓋率守衛本身失效**               | 全部                           | 釘死分母                     |
| 4 · 量不到覆蓋率的 package               | 327 行＝29% 目標               | 再釘 1 支                    |
| 5 · 就地掏空                             | 無上界                         | 第六道守衛                   |
| 6 · **格式漂移** —— 迴圈跑起來之後才發現 | 六項全綠會放它過去             | 補第 0 道 `vp check`         |

第 6 條是唯一一條在**迴圈運行中**而不是架設施時發現的：第三輪把逐 `it` 的
timeout 提到 `describe` 上之後 `oxfmt` 不接受那個排版，而當時的六道守衛
一項都沒紅。

## 三、三個獨立於本題成立的發現（關於真的那棵樹）

### ⚠️ 1. `tools/` 的覆蓋率數字今天是假的

`vite.config.ts` 裡**沒有任何 coverage 設定**，所以分母只含「被載入過的」
檔案。後果不是精度問題，是**方向問題**：刪掉一支測試，它的受測對象整支從
分母消失，覆蓋率不會下降。差分實測：

| 刪 `tools/gate-kit/tests/walk.test.ts` | 之前 | 之後     |
| -------------------------------------- | ---- | -------- |
| 預設射程（＝今天的實況）               | 100% | **100%** |
| `--coverage.include='src/**'`          | 100% | **65%**  |

同一個設定也讓 `tools/gate-kit/src/index.ts`（從未進過分母）、
`tools/codemods`（程式碼在 package 根層不在 `src/`，整支量不到 → 59.01%）
現形。**`tools/bff-check` 修不了** —— 它自己沒有產品碼，受測對象在
`platform/`，跨 package 拉不進分母。

釘死分母後的實況（17 個 package 量得到，`api-surface` 5.84%、`ui-survey`
11.53%、`exit-drill` 29.29%、`supply-chain` 29.50% 在低端）。

### 2. 這 32 支測試檔之間，8 行以上的跨檔重複是零

**逐字相同**與**把字串／數字換成佔位符之後**，兩種問法在 W=8 都是 **0**。
放寬到 W=6，字面值正規化後有 9 個視窗（上界 ~102 行，含大量重疊，實際遠低）。
偵測器兩個方向都驗過（注入一段 12 行重複 → 偵測到 5 個視窗；把每行換成唯一值
→ 0）。

⚠️ 這句話只涵蓋**長區塊的跨檔重複**，不等於「這套測試已經沒有可收割的抽象」。
而且真要抽出共用設施會需要**新增一個模組** —— 那要動 `SCOPE.md` 與
`gate-roster`，不在測試碼體積這個題目的射程內。

### 3. 格式化器會替重構加倍

第三輪拿掉逐 `it` 的第三參數（timeout）只刪了 13 行，而 `oxfmt` 隨後把原本
被迫多行的 `it(` 收成單行，又少了 **42 行**。⚠️ 反過來說：`checks.sh` 一開始
**沒有跑 `vp check`**，六項全綠會放格式漂移過去。已補成第 0 道。

## 四、⚠️ 一個擋住的門檻問題（需要人裁決，我不動它）

最大的一條機械路徑是把只差字面值的 `it` 區塊併成 `it.each`（上界 ~188 行，
29 組）。**第一輪實作了三塊，被第六道守衛駁回。**

而駁回的理由經不起檢查：

|                                          | `expect(` | `loc`       | 測試數 |
| ---------------------------------------- | --------- | ----------- | ------ |
| 對照 D —— 從通過的測試裡**拿掉兩行斷言** | 615 → 613 | 3507 → 3505 | 1451   |
| 第一輪 —— **合法的 `it.each` 併塊**      | 615 → 613 | 3507 → 3498 | 1451   |

**`expect(` 的差值一模一樣，測試數兩者都不動。** 唯一的差別是 `loc` 掉得
更多 —— 而那正是目標，所以合法重構的密度必然比掏空更差。**兩個計數器都
分不出「把三個相同斷言參數化成一個」和「刪掉兩個斷言」。**

這是這棵樹反覆出現的同一個形狀（C137 §四）：**判準套在東西的「描述」上，
不是「實質」上。** `expect(` 是語彙記號，不是執行到的斷言。

正確的儀器是**執行到的斷言次數**，而這一點**已經實測，不是推論**。用一支
一次性的 setup 檔（`expect.getState().assertionCalls`）在 `vue-typecheck` 上量
三個版本：

|                          | 執行到的斷言  | `expect(` 字面數 | `loc` |
| ------------------------ | ------------- | ---------------- | ----- |
| 現況                     | **74**        | 615              | 3445  |
| `it.each` 併三塊（合法） | **74** ← 不動 | 613              | 3446  |
| 拿掉兩行斷言（掏空）     | **72** ← 掉了 | 613              | 3443  |

**執行次數分得開，字面數分不開。** 量完立刻還原，禁區指紋逐條驗回（118 條
全對）。⚠️ 接上它需要 `test.setupFiles` —— vitest 4 的 CLI **沒有** `--setupFiles`
這個選項（會直接 `Unknown option` 失敗），所以必須改設定，而設定在禁區裡。

⚠️ **依 `AGENTS.md` 規則二，門檻訂錯要停下來告訴人，不得自己改。** 停在這裡。

## 五、可審的刪除提案

**沒有。** 三輪拿到的 62 行全部是重構（`beforeEach` 提取、timeout 提到
`describe`、格式收斂），沒有任何一行是刪掉測試。剩下的機械上界約 **95 行**，
分佈在六支檔案（`gate-roster` 20、`slice-gen` 12、`supply-chain` 11＋6、
`gate-kit` 5、`ui-survey` 5）—— 而那是**逐字相同的重複行數**，實作時要扣掉
提取本身的成本，`it.each` 那一組實測是負的。

要達成 30%，唯一剩下的來源是刪測試案例 —— 而那需要先回答「哪一條驗收
可以不要」，那是規格問題不是體積問題，**不在本次研究的射程內**。

## 七、「是不是沒有一支測試是多餘的？」—— 後續追問，答案是對的

⚠️ **§一～§六 回答不了這一題**，因為第六道守衛的第一句是「執行到的測試數
不得減少」——**刪掉任何一支都會紅，不管它有沒有用**。「沒刪成」是設計出來的，
不是量出來的。

換問法：**逐支拿掉，有沒有東西因此測不到了？** 兩關。

### 第一關 · 覆蓋率留一法（32 支全跑）

24 支拿掉會讓覆蓋率下降（最大的 `spec-report/report` 60.51% → 2.05%，
其次 `codemods/flatten-ui-theme` 59.01% → 6.01%）。3 支拿掉會讓**別的測試失敗**
（`gate-roster`、`pii-check`、`ui-survey` —— 它們之間有共用狀態，不是獨立的）。
**5 支 Δ0**，合計 249 行。24 ＋ 3 ＋ 5 ＝ 32。

⚠️ **這一欄原本寫 27，是算錯的**（27＋3＋5＝35，而只有 32 支）。量測台搬進版控
之後在**真樹**上重跑一趟校正：五支 Δ0 與三支「弄壞別人」的**檔案逐項相同**，
只有這個總數是錯的。

⚠️ **而那次重跑的第一趟六列回報「基線量不到」，那不是發現** —— 是當時樹上有一個
我自己造成的紅燈（見 §六）。**`base` 是 `None` 的那一列什麼都沒說**，不能讀成 Δ0。

其中兩支當場出局 —— 它們**根本沒有 `import ../src`**：

| 檔案                                                | 讀的是                                    |
| --------------------------------------------------- | ----------------------------------------- |
| `doc-facts/tests/cross-references.test.ts`（41 行） | `HANDOFF.md` 等文件（C99 的交叉引用規則） |
| `supply-chain/tests/renovate.test.ts`（81 行）      | `renovate.json`、`pnpm-workspace.yaml`    |

**覆蓋率對它們構造上是盲的** —— 這是本次找到的第七個盲區。

### 第二關 · 突變測試留一法（剩下 3 支）

射程 `tools/promise-check/src` ＋ `tools/slice-gen/src`＋`bin`。

| 拿掉                                                  | 殺掉的變異     | 存活 |
| ----------------------------------------------------- | -------------- | ---- |
| 基線                                                  | 300            | 122  |
| `promise-check/tests/probe.test.ts`（23 行）          | **282**（−18） | 140  |
| `slice-gen/tests/boundary-alignment.test.ts`（64 行） | 300            | 122  |
| `slice-gen/tests/spec-template.test.ts`（40 行）      | 300            | 122  |

`probe.test.ts` 殺掉 18 顆**沒有別人殺得掉**的變異 —— ⚠️ 覆蓋率 Δ0 卻是承重的，
這就是「Δ0 是必要條件不是充分條件」的直接證據。

### 剩下兩支：兩個工具都讀出零，而兩支都是承重的

讀它們在斷言什麼就結束了。`spec-template.test.ts` 自己寫著：

> 其餘的斷言都在讀字串……那些擋得住「模板被改壞」，**擋不住上游變了**：
> runner 換掉 `predefinedSteps` 的形狀、或中文關鍵字表改版，字串斷言全都
> 還是綠的，而破掉的東西會落在第一個產切片的專案組手上。

它把模板產出的 `.feature` 餵進**真的 parser**。`boundary-alignment.test.ts` 同理 ——
它斷言產生器的輸出**過得了 D4 第 2／3 層的 ESLint 規則**（而且自帶一條
「確實有掃到原始碼檔案（避免測試本身空轉而假性通過）」的反空轉斷言）。

**兩支的受測對象都不是 `slice-gen` 的 `src/`，而突變測試的分母只有 `src/`。**
那個零是構造上的零。

而這正是 **D16 的迭代軸**：「上游變了的時候，它會不會告訴你哪裡壞了」。
D16 自己記錄的樣本是同一個形狀（vitest 4 移除 `--reporter=basic`，子行程啟動即
失敗而失敗清單是空的 —— **空清單和全綠長得一模一樣**）。

### 結論

**32 支裡沒有找到一支是多餘的。** 每一支不是動了覆蓋率、就是殺掉別人殺不掉的
變異、再不然就是守著一份兩個工具都量不到的上游契約。

⚠️ 而這一節本身示範了本次研究反覆出現的那件事：**四支測試被兩個量測工具讀成
零，四支都是承重的，四支的受測對象都不是本地的 `src/`。** 判準套在工具看得見的
東西上，答案會很漂亮而且是錯的。

## 六、射程與不做的事

- 結論適用範圍是 `tools/`。**不產出「該加／該刪哪一支閘門」的結論** —— C137 §一 明文禁止。
- 突變分數的可見度數字（conformance 237 顆有 72 顆不可見、逐檔 4%～57%）
  是引用既有量測，本次**沒有重量**。§七 的突變測試是新跑的，射程只有兩個 package。
- ⚠️ **跑 stryker 會把 16 個 `tools/*/src/cli.ts` 的模式 100755 → 100644**（內容
  零變更）。守它的閘門只看 index 不看工作區，所以不會紅。每次跑完要
  `git checkout -- .`。本次實測的只有「19 支檔、5,864 行」這個
  位置，以及「子行程跑的 CLI 覆蓋率是 0%」這個構造事實。

### ⚠️ 把量測台搬進版控時，這棵樹的閘門當場抓到我一次

`mutation-loo.sh` 我給了 100755。C122 的檔案模式規則說：版控裡的 100755 必須有
某個 `package.json` 把它宣告成 `bin` —— 而 `reports/research/rigs/` 沒有
`package.json`（那正是它不放 `tools/` 的理由）。

**而 `git add` 之前的 `vpr ready` 是綠的**，因為那道閘門讀的是版控。commit 之後
才紅，紅的地方還不是閘門本身，是 `slice-gen` 的 e2e 測試 —— 它跑真的 conformance
並斷言「違規恰好一項」，我的檔案讓它數到兩項。

⚠️ **要改的是檔案不是閘門**（`AGENTS.md` 規則二），所以 `mutation-loo.sh` 是
100644，用 `bash` 起。⚠️ 而那趟紅燈期間跑的留一法整份作廢 —— 六個 package 的
基線覆蓋率量不到，讀起來像新發現。**先確認樹是綠的，再開始量。**
