# 測試模型選型與邊界有效性 —— 「五層兩類」vs 「五角色表」

**量測基準 commit**：`19c0c06`（C156 合併當天，2026-09-01）

⚠️ **聲明**：本報告是觀察，不是判準。不得拿其中任何主張論證任何閘門的增減或設定的改動。

---

## 一、問的是什麼

C156 在 9 月 1 日明確拒絕了「五角色 × 工具」的提案表，理由是**它評的是另一套座標系統之外的東西**。問題變成：

1. 這兩個模型各自守住了哪些失敗模式、放過了哪些？
2. 「最少的測試項目」用什麼尺量？
3. 它們混起來會比單用其中一個更好嗎？
4. 目前導入的哪些工具應該移除？

本報告逐項回答，每一項都附出處。

## 二、兩個方案的測試邊界定義

### 2.1 「五層兩類」框架（現況）

**定義出處**：`TESTING.md` 第 2–5 節、C114、C115、C119、C121

「五層兩類」是一個二維座標，**兩軸正交**：

- **五層**（借用 Robert C. Martin 的討論）：約束 → 單元 → 驗收 → QA → 手動
- **兩類**（這棵樹的身分）：**第一類**（框架自己）vs **第二類**（交付給專案組的能力）

| 層        | 第一類（框架測試）                  | 第二類（交付的測試設施）          |
| --------- | ----------------------------------- | --------------------------------- |
| 層 1 約束 | `vp check`（Oxfmt、Oxlint、複雜度） | 同一套設定隨 v1 下發              |
| 層 2 單元 | Vitest，無下限門檻                  | Vitest，下限在 usecase 層（C120） |
| 層 3 驗收 | 一條承諾（`promise-check`）         | 規格設施齊、內容空（C114/C115）   |
| 層 4 QA   | 沒有                                | 沒有，**下發不了**                |
| 層 5 手動 | 沒有                                | 沒有，**下發不了**                |
| 元層 突變 | Stryker 10.0.0（清單，無門檻）      | 同一份設定涵蓋產品碼與示範應用    |

**關鍵特徵**：

- **第一類是斷言邊界**：十幾道閘門，每道附反向測試（C121 §五）
- **第二類是能力邊界**：不光是驗證框架，而是**交付給 fork 去做案子的團隊能拿起來就用的東西**
- **兩類的失敗模式不同**：第一類紅了是維護者的問題，第二類紅了是專案組的問題

**量得到的失敗模式**（現有機制能擋下的）：

| 失敗模式                               | 機制                                               | 誰能看到                 |
| -------------------------------------- | -------------------------------------------------- | ------------------------ |
| 程式碼紋路（複雜度超、cycle 依賴）     | `vp check` + Oxlint + `tools/conformance`          | 第一、二類都看得到       |
| 層級邊界破裂（相對路徑逃逸、幽靈依賴） | `tools/conformance`                                | 第一、二類都看得到       |
| 驗收承諾不兌現（API 後相容、安全邊界） | `tools/promise-check`（一條）、`tools/api-surface` | 第一類                   |
| 測試沒在測（沒人審的測試是空頭支票）   | Stryker 清單（無門檻）                             | 第一類                   |
| 規格通過率                             | `tools/spec-report`                                | 第二類（但目前規格為空） |

**量不到的失敗模式**：

- 層 4（QA 程序）、層 5（週期性手動測試）—— **刻意下發不了**（TESTING.md §三 §四 §五）
- `<script setup>` 的複雜度（模組層在四維規則裡不存在）—— TESTING.md §三「層 1 約束」
- `.vue` 的 mutation —— stryker.config.mjs 行 178–180 的註記，.vue 不在射程

### 2.2 「五角色 × 工具」表（提案，已否決）

**提案出處**：使用者的表格；C156 §二 指出它的問題

| 角色   | 層次 | Vite+ / Vue 對應            | C156 的判詞                 |
| ------ | ---- | --------------------------- | --------------------------- |
| 規格員 | 層 3 | Playwright + playwright-bdd | 前提打錯對象（§四）         |
| 撰寫員 | 層 2 | `vp test` + `vi.mock` + MSW | 樹上零個 test double（§五） |
| 清理員 | 層 1 | `vp check` + CRAP Score     | 兩個因子各自半盲（§六）     |
| 強化員 | 元層 | Stryker                     | 已在樹上（§七）             |
| QA 員  | 層 4 | Vitest Browser Mode         | 標籤錯誤（§八）             |

**C156 對每列的核心主張**：

1. **第 1 列**（規格員）：提案評的是「瀏覽器 Gherkin（Playwright 驅動）投報率低」，但這棵樹的層 3 是**Vitest 驅動、打 usecase 層的 Gherkin**（C114）。兩個完全不同的東西。
   - **驗證**：搜尋結果確認 playwright-bdd 存在且有 2024–2025 的活躍開發，但沒有針對「投報率」的定量評估。
   - **這棵樹的對應物**：`@amiceli/vitest-cucumber` 7.0.0，在 `promise-check`、`slice-gen`、`spec-report` 三支工具中使用。

2. **第 2 列**（撰寫員）：C156 表 §五 實測射程 `apps/`、`platform/`、`tools/`、`features/`、`specs/`，`vi.mock` **0 次**、`vi.stubGlobal` **0 次**、`vi.spyOn` **0 次**，而對照組 `startBffMock` **6 次**。
   - **驗證結論**：樹上確實零個 test double（vi.mock 形式），使用了 `platform/bff-mock` 的參考實作 + `tools/bff-check` 的契約驗證。MSW 會是新增一種手法，不是取代。

3. **第 3 列**（清理員）：CRAP = CC² × (1 − cov/100)³ + CC（Savoia & Alberg 2007）。
   - **oxlint 沒有 CRAP 規則**（`vp lint --print-config` 確認：`complexity` 有、CRAP 無）。
     ⚠️ **但公式那一句不是一手來源核過的** —— 引到的是 Better Stack／NCover／GMetrics
     三份二手整理，Savoia & Alberg 的原文沒有取到。**公式在這份稿子裡是待驗的。**
   - **C156 的指控**：複雜度那一維 `<script setup>` 在四條規則裡不存在（TESTING.md §三 §六），覆蓋率在 package 層寫錯不會報錯（TESTING.md §四）。兩個半盲相乘的數字看起來權威但虛假。

4. **第 4 列**（強化員）：Stryker 10.0.0 已在樹上（stryker.config.mjs 行 117，`@stryker-mutator/core` 與 `@stryker-mutator/vitest-runner` 釘死 10.0.0）。
   - ⚠️ **本報告初稿在這裡寫了一句自相矛盾的話，已撤回**：「WebSearch 確認最新版本
     9.1.1」與「樹上釘死 10.0.0 且跑得動」不可能同時成立。**磁碟是事實來源** ——
     `node_modules/.pnpm` 上 `@stryker-mutator/vitest-runner@10.0.0` 實體存在，
     全樹跑過（C121 記的 78 支產品檔／6,125 個 mutant／0 errors）。
     那個 9.1.1 是搜尋噪音，**不採用**。C108 已驗過兩個真阻斷都有繞法。

5. **第 5 列**（QA 員）：Browser Mode 被貼成「層 4」（QA 程序），但層 4 是**下發不了的人做的事**。正確的講法是「層 2／3 換執行基底」（happy-dom → 真瀏覽器）。
   - **驗證**：Vitest 4.1.10 支援 browser mode，三個 provider（Preview、Playwright、WebdriverIO）。成本實測：`@vitest/browser` 已隨 vite-plus 進來（3 個實體），但 Playwright provider 與瀏覽器二進位未裝。

**「五角色表」的測試邊界定義方式**：

該表只帶了「五層」這一軸，**漏掉了「兩類」這一軸**。結果是：

- 層 1–3 的兩類差別消失（無法判「第一類內改動會不會打斷第二類」）
- 層 4–5「下發不了」的屬性不可見（無法判「這個工具能交付不」）
- 五層座標本身只描述第一類，用它量第二類的機制時測不了（C156 §二的表格）

## 三、「最少的測試項目」的量法定義

### 3.1 什麼不是「項目」

⚠️ 首先排除四個容易混淆的尺度：

| 常見尺度         | 為什麼不適用                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------- |
| **總 runner 數** | C87 已踩過一次：兩支 runner 搶同一個 repo 時排程相依會紅，第二套 runner 會再撞一次同一個問題 |
| **工具數量**     | 「tool 多」與「測試邊界有效」無關（C156 §三 舉例：runner 1 → 3，但那不是好事）               |
| **相依層數**     | 水平相依（多個 runner 搶資源）比深度相依（層層调用）更危險；只算層數會漏掉橫向的坑           |
| **內存佔用**     | 與測試**邊界**無關；與**可維護性**有關，但兩者不同（C137 §一 明文禁用）                      |

### 3.2 什麼是「項目」：可執行的檢查單位

**定義**：一個**不可再分的檢查單位**，必須同時滿足：

1. 有獨立的執行時間邊界（可以單獨 spawn 或不 spawn）
2. 有獨立的失敗模式監察（紅了能指名是哪一層的問題）
3. 有獨立的前置條件與清理（改動某一層的程式碼不必重執行另一層的檢查）

**現況的檢查單位**：

| 檢查單位         | 執行方式                                           | 前置條件             | 失敗模式                         |
| ---------------- | -------------------------------------------------- | -------------------- | -------------------------------- |
| **約束（層 1）** | `vp check`                                         | 無                   | 格式、lint、型別、複雜度         |
| **單元（層 2）** | `vp run -r test`                                   | 層 1 通過（隱含）    | 程式碼邏輯錯誤、邊界案例         |
| **驗收（層 3）** | `vp run <pkg>#test` via `@amiceli/vitest-cucumber` | 層 1、2 通過（隱含） | 規格場景失敗                     |
| **突變（元層）** | `pnpm exec stryker run`                            | 層 1、2、3 通過      | 測試被殺死數（清單，無門檻）     |
| **切片契約**     | `tools/conformance`                                | 層 1 通過            | 分層邊界、幽靈依賴、相對路徑逃逸 |
| **相容性**       | `tools/api-surface`                                | 層 1、2 通過         | 基準檔與產品碼差分               |

**計數方式**：**檢查單位數 = 失敗模式種類數**

| 失敗模式              | 檢查位置                                             | 開銷（相對）      |
| --------------------- | ---------------------------------------------------- | ----------------- |
| 格式 ✅               | `vp check`（Oxfmt）                                  | 中                |
| Lint（對/錯/風格） ✅ | `vp check`（Oxlint）                                 | 中                |
| 型別 ✅               | `vp check`（tsdown/tsgolint）+ `tools/vue-typecheck` | 中                |
| 複雜度 ✅             | `vp check`（Oxlint 規則）                            | 低                |
| 邏輯錯誤 ✅           | `vp run -r test`（Vitest）                           | 高                |
| 規格場景 ✅           | Vitest cucumber runner                               | 中（已內建 #114） |
| 分層邊界 ✅           | `tools/conformance`                                  | 中                |
| 相容性 ✅             | `tools/api-surface`                                  | 高                |
| 測試空心 ✅           | Stryker（清單）                                      | 很高              |

**數字**：**目前 9 個失敗模式，由 8 個執行位置守著**（層 3 的規格與層 2 的單元測試同一個 runner，但監察的是不同的模式）。

## 四、混合方案：有、但形狀受限

### 4.1 理論上能混入的工具

C156 表面上否決了全部五列，但實際上：

| 工具           | 現況                            | 能否混入        | 原因                                                              |
| -------------- | ------------------------------- | --------------- | ----------------------------------------------------------------- |
| Playwright-bdd | 未裝                            | ❌ 不該         | 層次對象差別大（usecase vs e2e）；無定量投報率數據                |
| vi.mock + MSW  | 未裝                            | ✅ 可以，但不必 | 樹上已用 BFF mock 替代；若要用須評估**為什麼**（C155 §五 的教訓） |
| CRAP Score     | 無工具                          | ❌ 不該         | 依賴兩個都不完整的量測，相乘放大誤差（C156 §六）                  |
| Browser Mode   | 裝了（`@vitest/browser`）但未用 | ⚠️ 待裁         | 需要自己的 D16 兩軸報告（C154 §四、C156 §八）                     |

### 4.2 Browser Mode 的 D16 評估（現況資料）

**定義出處**：D16（DECISIONS.md 根層、C142）

D16 要求逐支問兩軸：**交付軸**（有沒有對上游改動時的新姿態）和**迭代軸**（壞法有沒有安靜）。

#### 交付軸：有新的著力點

Browser Mode 對標現有能力的對應：

| 現有能力          | 覆蓋工具                                       | Browser Mode 的差別                              |
| ----------------- | ---------------------------------------------- | ------------------------------------------------ |
| **Teleport 測試** | 現況：renderToString（空）+ jsdom mock         | Browser Mode：真實 DOM、Teleport 可見            |
| **無障礙名稱**    | 現況：textContent 代理（缺陷與非缺陷紅同一組） | Browser Mode：可取 `aria-label`、role 推導       |
| **CSS 狀態**      | 現況：`.vue` 不在 Stryker 射程                 | Browser Mode：可測真實樣式（但須新增瀏覽器 dep） |

**小結**：Browser Mode 有**三個已知的量度不到的盲點可補**（TESTING.md §三 §五 與 §六），也就是說**有交付價值**。

#### 迭代軸：壞法有沒有安靜

**通過判準**（C142 §一）：① 對象在外（Vitest runner 本身由 vite-plus 管）② 壞法安靜（Vitest 開發不會默默破壞 browser mode）

**驗證**：

- Vitest 4.1.10 支援 browser mode（官方文檔確認）
- `@vitest/browser-playwright` 是 optional peer（pnpm-lock 裡沒裝），**對象在外** ✅

⚠️⚠️ **本節初稿把 ② 問錯了，已更正。** 初稿的待測項是「provider 未裝時
`vp test --browser` 會紅還是靜默回綠」—— **那是在問工具穩不穩，不是 C142 §一 的 ②。**
C142 的 ② 問的是：**在這個檢查不存在的世界裡，被守的那個東西壞掉時看起來是不是綠的。**

按正確的問法，② **已經有答案，而且答案是「安靜」**：`platform/ui` 今天走 happy-dom，
而樹上記著兩個盲點 —— Teleport 在 `renderToString` 下一個字都沒有、可及名稱走
textContent 代理**讓缺陷與非缺陷紅同一組**。**這兩種壞法今天全綠。**

**順帶實測了初稿那個（不同的）問題，結論是它不靜默**（基準 `19c0c06`）：

| 情境                                       | 結束碼 | 輸出                                                                                        |
| ------------------------------------------ | ------ | ------------------------------------------------------------------------------------------- |
| `vp test --browser`（樹上零 browser 設定） | **1**  | `Startup Error: Vitest received --browser flag, but no project had a browser configuration` |

⚠️ **這一格只答了「設定缺席」那一種**。「設定在、provider 套件不在」沒有量 ——
要量它得先寫一份 browser 設定，而那已經是導入的第一步，不是評估。

## 五、該移除哪些已導入部分

### 5.1 移除評判框架

一個東西該移除的充要條件：**移除之後，某個失敗模式沒有人在守了，且無替代機制**。

### 5.2 逐項評估

#### 可以考慮移除：MSW（如果有的話）

**現況**：MSW **未裝**（pnpm-lock 查詢無結果）

**為什麼可以不裝**：

- 樹上已用 `platform/bff-mock`（參考實作）+ `tools/bff-check`（契約驗證）的組合
- 該組合**測得到飄移**（契約改了，bff-check 會紅）
- MSW 是手寫副本，**測不到飄移**（handler 改了 bff-check 照樣綠）

**判斷**：MSW 在這棵樹的環境下沒有增益，不必新增。

#### 不該移除：@amiceli/vitest-cucumber

**現況**：7.0.0，在三支工具中使用

**為什麼不該移除**：

- 移除之後，層 3 的驗收規格無人執行（`@amiceli/vitest-cucumber` 是唯一載體）
- 「專案成員只需要補 TDD 就能量出完成率」這句承諾直接掛在它上面（TESTING.md §四「第二類的現況」）
- ⚠️ **本報告初稿在這裡寫錯了一句，已撤回。** 原句是「#145 實測到四個真缺口，其中三個
  由它驅動的規格發現」。`TESTING.md:186` 說的相反：**#145 是三處不是四個，而且它們
  「不是手寫想出來的，是機械跑一遍掉出來的（#136）」** —— 來源是 Stryker，不是規格。
  （`register.ts:51` 那一顆屬於 #163，不是 #145，檔名也不是 `composition-root.ts`。）
  **結論不變，但它靠的是 C114／C115／C118，不是 #145。**

**守著的失敗模式**：規格場景失敗（層 3）

#### 不該移除：Stryker 10.0.0

**現況**：裝著，無門檻（thresholds.break = null）

**為什麼不該移除**：

- 移除之後，「沒人審的測試是不是空頭支票」無人守（元層的唯一驗證機制）
- 產出是清單不是分數，不擋東西（所以無法被「通過門檻」來正當化移除）
- 已踩過的坑有正式記錄（C121 §五、§六）

**守著的失敗模式**：測試空心（元層）

#### 不該移除：Oxlint 複雜度規則（層 1）

**現況**：四條規則（max-lines / max-depth / max-params / complexity），釘在 vite.config.ts

**為什麼不該移除**：

- 移除之後，「agent 把自己纏進去」的程式碼無人擋（TESTING.md §三 §一 的最初理由）
- C119 決策時已附四則 C 編號當論證（該回過頭去讀那些編號來看是否仍然成立，**本報告不重做那個判斷**）

**守著的失敗模式**：程式碼複雜度超標（層 1）

### 5.3 明確不能移除的三個組合機制

| 機制                                           | 失敗模式                         | 移除後的後果                             |
| ---------------------------------------------- | -------------------------------- | ---------------------------------------- |
| `tools/conformance`                            | 分層邊界、幽靈依賴、相對路徑逃逸 | 第一類的三個邊界保護全部失效             |
| `tools/api-surface`                            | 基準檔與產品碼飄移               | 升級平台時無法預警「會不會打斷下游切片」 |
| `tools/api-surface` ＋ `tools/codemods` 的搭配 | 升級後的補救                     | 無法自動化手改缺口（切片升級代價太高）   |

## 六、主要發現

### 6.1 「五角色表」為什麼不合用

它不是「一個更簡潔的表達」，而是**少掉了一整個維度**。那個維度不是附加，而是根本：

> 五層問的是「哪一層在守」，兩類問的是「為誰而守」；拿五層量五層，對；拿五層量兩類，測不到。

C156 的表格（§二）列了七個「五層量不到」的機制，其中五個是在守「飄移」（平台改動時的副作用）。角色表一格都沒有。

**具體例**：C109 時 `slice-gen` 被判「不是測試層」（用五層的尺），改成「第二類的入口」（用兩類重量）之後判決反轉。**同一支工具，不同的尺，相反的結論**。

### 6.2 CRAP Score 的兩個因子都有已知盲區

| 因子          | 盲區                                                                                                  | 覆蓋率                                               |
| ------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 複雜度（CC）  | `<script setup>` 的 module 層在四條規則裡不存在；`platform/ui` 的 24 個 .vue、1992 行 script 分佈為 0 | `platform/ui` 相對的無盲區（Vue 元件可測）           |
| 覆蓋率（Cov） | 預設射程會讓未載入的產品碼整支不進分母；射程逐 package 不同且寫錯不會報錯                             | 單一 package 內有人把持得住，但多 package 時容易出錯 |

CC² × (1 − Cov/100)³ 的結果看起來精確，但實際上是「兩個都不完整的量測相乘放大誤差」。TESTING.md §六 對此的評價是「一道經常因為無關原因變紅的閘門，結局是被關掉，而被關掉的閘門連清單都產不出來」。

### 6.3 Browser Mode 還有一張待簽的支票

現有配置是 `@vitest/browser` 4.1.10（已隨 vite-plus 進來），但 Playwright provider（`@vitest/browser-playwright`）未裝。

**Playwright provider 的成本**：

- 新增一層 package 依賴（`@vitest/browser-playwright`）
- 新增瀏覽器二進位（Playwright 內建）
- 會動到 `supply-chain`／airgap 那條線（SCM 管理的新增項）

**Browser Mode 的交付價值**：Teleport rendering 與無障礙名稱推導的真實測試能力（TESTING.md 有兩處記載現有工具的盲點）

**待決**：D16 兩軸報告（C154 §四、C156 §八 明文要求）

### 6.4 Runner 數不是好的最小化尺度

提案聲稱「減少導入測試種類」，但實際效果是 runner **1 → 3**（Vitest ＋ Playwright ＋ Browser Mode Vitest）。

**為什麼不用 runner 數當尺度**：

1. C87：兩個 runner 搶同一個 repo 時已踩過排程相依的坑
2. 同一個 runner 內的差別可能更大：Vitest 的 jsdom 環境 vs browser 環境，設定一樣但行為不同
3. 真正的成本不在「幾個 runner」而在「有沒有新的橫向相依」（D16 迭代軸的「壞法有沒有安靜」）

## 八、建議

### 8.1 保持現狀

**五層兩類 + 現有工具組合** 已經答得清楚的問題：

- 程式碼對不對（層 1–3）
- 測試在不在（元層）
- 平台升級會不會打斷下游（相容性軸）

**不需要新增**：

- MSW（現有 BFF mock + 契約驗證夠用）
- Playwright-bdd（層次對象差別大）
- CRAP Score 的工具支援（因子盲區無法補）

### 8.2 待決項

**Browser Mode**：尚需補充 D16 兩軸的完整報告才能判。關鍵待測：

- ✅ 交付軸：有三個已知盲點可補（Teleport、無障礙名稱、CSS 狀態）
- ⚠️ 迭代軸：需驗「Playwright provider 未裝時會不會靜默失敗」

### 8.3 不該移除的清單
