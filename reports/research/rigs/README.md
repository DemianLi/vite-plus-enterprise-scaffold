# 量測台 —— 「拿掉這支測試，會不會有東西測不到」

這裡放的是 [`../test-volume-30pct-2026-08-29.md`](../test-volume-30pct-2026-08-29.md)
那份報告裡每一個數字的**產生器**。報告是凍結的結論，這裡是可以再問一次的問句。

> ⚠️ **這個目錄沒有任何機制在守。**
> `SCOPE.md` 的 `reports/` 那一列就是這樣寫的，而它對這裡一字不改地成立：
> 上游改了旗標、換了名字，這裡不會紅 —— 會**安靜地量錯**。所以每一支腳本都自帶
> 對照組的說明，而拿數字下判斷之前先確認對照組還有反應。
>
> ⚠️ **這裡的東西不是閘門，也刻意不在 `tools/` 底下。** 它們回答的是給人判斷用的
> 問題，不是紅線。任何一支都不得接進 `scripts.gate` 或 `scripts.ready`。

## 四支腳本，三個關卡

| 腳本               | 它回答什麼                                       |
| ------------------ | ------------------------------------------------ |
| `loc.py`           | 這批測試現在有多大，而縮小它的時候有沒有真的縮小 |
| `coverage.py`      | 逐 package，產品碼有幾成被測試走過               |
| `leave-one-out.py` | **第一關**：拿掉這一支，覆蓋率會不會掉           |
| `mutation-loo.sh`  | **第二關**：拿掉這一支，會不會有新的變異活下來   |

**第三關是人。** 兩關都讀 Δ0 的檔案，要去讀它自己寫的檔頭 —— 實測四支被兩個工具
讀成零的測試，四支都是承重的，四支的受測對象都不在本地 `src/`。經過見報告的 §七。

⚠️ **Δ0 是冗餘的必要條件，不是充分條件。** 反例有數字：`promise-check/tests/probe.test.ts`
覆蓋率 Δ0，拿掉它有 18 顆變異從「被殺」變成「存活」。

## 跑之前

```bash
python3 reports/research/rigs/loc.py
python3 reports/research/rigs/coverage.py > /tmp/cov.json
python3 reports/research/rigs/leave-one-out.py > /tmp/loo.json   # 進度走 stderr
bash reports/research/rigs/mutation-loo.sh tools/promise-check/tests/probe.test.ts
```

⚠️ `mutation-loo.sh` **刻意不是可執行的**（100644，所以用 `bash` 起）。
C122 的檔案模式閘門要求版控裡的 100755 必須有某個 `package.json` 把它宣告成 bin ——
而這個目錄沒有 `package.json`，那正是它不放在 `tools/` 底下的理由。
⚠️ 這道閘門讀的是**版控**：檔案還沒 `git add` 之前它看不見，`vpr ready` 會是綠的。

⚠️ 後兩支**要求工作樹完全乾淨**（含未追蹤檔），跑之前先 commit 或 stash。
理由不是潔癖：它們把測試檔搬開再搬回來，而 `mutation-loo.sh` 的還原路徑走
`git checkout -- .`（從 index 覆蓋工作區）—— 髒樹上跑會吃掉未提交的修改。
這道守衛是「從實驗室搬回真樹」造出來的需求：在拋棄式的 clone 裡留下一個 `.off`
殘骸無所謂，在這裡不是。

⚠️ **`mutation-loo.sh` 每跑一趟會把 16 個 `tools/*/src/cli.ts` 的模式 755→644**，
內容零變更 —— 而守模式的閘門只看 index 不看工作區，**所以它不會紅**。腳本每趟
結束都還原，並且在中斷時也還原；手動跑 stryker 的話自己記得看 `git diff --summary`。

## 為什麼指標長這樣

六條「達標而什麼都沒改善」的路徑（清空註解、掏空斷言、刪掉覆蓋率量不到的那批……）
以及每一條是怎麼被堵住的，寫在報告的 **§二**，這裡不重抄 —— 同一件事抄兩份而沒有
東西斷言它們一致，是這棵樹反覆付過代價的病（`SCOPE.md`〈三份清單，三條軸〉）。

指標本身的設計理由留在各腳本的 docstring 裡，那是承重的部分。

## 一個沒有解決的門檻問題

`expect(` 的**字面量數**與**執行到的斷言數**會分岔：合法的 `it.each` 合併讓字面量
從 615 掉到 613 而執行數 74 一動不動，掏空則讓執行數掉到 72。用字面量當守衛會擋掉
合法的重構、放過真正的掏空。要量執行數得走 `test.setupFiles`（vitest 4 沒有
`--setupFiles` 這個 CLI 旗標）—— 那是改設定，依 AGENTS.md 規則二不自己動。
細節與那張三列的表在報告的 §四。
