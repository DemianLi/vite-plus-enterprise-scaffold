# @org/supply-chain

R2／R3／R4／R5／R8 的技術處置。

## 五條風險是同一個問題

風險登記簿把它們列成五條，但它們共用一個根因：
**沒有人手上有一份「這個 repo 到底拉了什麼進來」的準確清單。**
於是每一條都被迫用人腦估計 —— 而估計錯了。

| 登記簿原本寫的                          | 實際                                                             |
| --------------------------------------- | ---------------------------------------------------------------- |
| 「8 個平台原生二進位」                  | **121 個**，分屬 **11 個家族**                                   |
| 「證據：npm 上的 SLSA provenance」      | 只涵蓋 **89 個**；另 32 個（含 TypeScript 7）**沒有** provenance |
| 「內部 registry 須鏡像全部 8 個平台包」 | 467 個套件，其中 19 個住在 lockfile 的**第一份 YAML 文件**裡     |
| 「須改 `onFail`」                       | 實測**無效**。`onFail` 不是下載的開關                            |

差 15 倍的那一條最危險：拿那份清單去申請 SCA 例外，例外會照著它核准，
然後 CI 在沒被核准的另外 113 個上面掛掉。

所以這裡不逐條處理，而是把清單**算出來**，讓五條各取所需。

## 用法

```bash
vpr supply-chain          # 離線閘門（已在 gate 與 Tier 2 裡）
```

| 指令                   | 連網？ | 給誰                                         |
| ---------------------- | ------ | -------------------------------------------- |
| （預設）               | 否     | 閘門                                         |
| `vpr sca-dossier`      | 否     | **資安** —— SCA 例外申請書                   |
| `vpr mirror-manifest`  | 否     | **平台／IT** —— 含 sha512 的鏡像清單         |
| `vpr airgap`           | 否     | **平台／IT** —— 封閉網路前置條件與驗收方式   |
| `--update`             | 否     | 維護者 —— 重算 `inventory.json`              |
| `--capture`            | **是** | 維護者 —— 重新擷取 `provenance.json`（季度） |
| `--verify-sbom <path>` | 否     | CI —— 驗 SBOM 不是空的（見下）               |

三份給人看的文件都是**產生**的，不是寫的。手抄的數字正是這件事最初出錯的原因。

## 閘門守著什麼

| 檢查            | 擋下的情況                                                              |
| --------------- | ----------------------------------------------------------------------- |
| 未分類家族      | 新的原生工具鏈進到建置環境，還沒有人說它是什麼                          |
| 基線漂移        | 原生套件清單或 integrity 有變                                           |
| 平台覆蓋        | 某個工具鏈家族缺少目標平台的變體（**R3 的實際失敗模式**）               |
| 來源綁定        | lockfile 的 digest 與擷取當下記錄的不符                                 |
| 建置腳本        | 有原生套件被列入 `allowBuilds`（申請書宣稱它們不執行腳本）              |
| frozen-lockfile | CI 的安裝步驟少了 `--frozen-lockfile`（申請書第一條補償控制）           |
| 產生器範圍      | `bingo` 洩到 `apps`／`features`／`platform`（**R8**）                   |
| SBOM 完整性     | 掃描器產出的 SBOM 是空的或明顯少於 lockfile（`--verify-sbom`，CI 專用） |

**逐一破壞這七項共十種情況，每一種都讓閘門紅在正確的那一條上。**
綠燈不證明機制有效，只有「該紅的時候會紅」才證明。

## R4：為什麼不需要把 attestation 搬過 proxy

登記簿寫「provenance attestation 過 proxy 會遺失，須另存來源證明」。
前半句是對的，後半句把問題想得比實際難。attestation 綁定來源的方式是 digest：

```
attestation.subject[0].digest.sha512   ← tarball 的 sha512（hex）
pnpm-lock.yaml 的 resolution.integrity ← 同一個 sha512（base64）
```

**這兩個是同一個數字的兩種編碼。** 所以只要 lockfile 的 integrity 沒變，
proxy 送來的那顆 tarball 就是被 Sigstore 簽署過的那一顆 ——
proxy 有沒有保留 attestation 都無所謂。

⚠️ 這裡有**兩個覆蓋範圍不同的斷言**，剛好都跟 121 有關，很容易講混：

| 斷言                                               | 涵蓋    | 何時跑      | 抓什麼                    |
| -------------------------------------------------- | ------- | ----------- | ------------------------- |
| lockfile integrity ＝ 擷取當下記下的 integrity     | **121** | 每次 gate   | 同一版本號換了內容物      |
| 擷取當下的 integrity ＝ attestation subject digest | **89**  | `--capture` | 編碼等價（R4 論證的本體） |

第二條只有**有 attestation 的那 89 個能比**，覆蓋率 74%。剩下 32 個
（`@typescript/*` 20、`lightningcss-*` 11、`fsevents`）的補償控制是
npm 發佈簽章 ＋ lockfile 的 digest 釘選。把 89 說成 121 會在資安抽驗
`@typescript` 時當場破功。

處置因此拆成兩半，跟 `tools/exit-drill` 同一個形狀：

- **擷取**（`--capture`）要連公網。在還連得到 `registry.npmjs.org` 的環境跑，
  把 digest、來源 repo、commit、建置 workflow 抄進 `provenance.json` 並進版控
- **驗證**（預設，跑在閘門）不連網。只比對 integrity 是否仍等於擷取當下的值

> ⚠️ **這對發版流程有一項硬性限制**：在封閉環境裡**升相依無法就地完成**。
> 改 lockfile 與跑 `--capture` 必須在還連得到公網的那一側做完，兩份檔案一起進來。
>
> 這是設計的結果不是缺陷 —— 反過來讓閘門自己連公網補資料，它就會在最需要它的
> 環境裡失效。請把這一條寫進發版流程，別讓人在封閉環境裡對著紅燈找原因。

## R2：佐證必須分兩級

| 佐證            | 數量 | 能證明什麼                          |
| --------------- | ---- | ----------------------------------- |
| SLSA provenance | 89   | 可回推到來源 repo 的**確切 commit** |
| 僅 npm 發佈簽章 | 32   | 可驗發佈者，**無法回推建置來源**    |

第二級包含全部 20 個 `@typescript/typescript-*` —— 也就是 **TypeScript 7 自己**。
拿「證據是 SLSA provenance」這句話去申請例外，會在覆核時當場破功。

順帶一提，這也把申請的性質改掉了：`@typescript` 與 `lightningcss` 都不是
vite-plus 帶來的，而是「現代前端工具鏈普遍原生化」的結果。要談的因此是
**原生編譯工具鏈的政策**，一次核准；不是逐個廠商申請例外。

授權也不是一句「都是 MIT」：`lightningcss` 是 **MPL-2.0**，
22 個 `@yuku-*` 在 registry 上**沒有 license 欄位**。後者本工具刻意不從上層
套件推斷 —— 那等於代發佈者做法律聲明。兩件都要法務點頭。

## R5：登記簿的處置寫錯了

實測四種設法（每次開乾淨的 HOME、指定尚未快取的 pnpm 版本，
再看 pnpm 的 metadata 快取目錄以哪個 host 命名）：

| 設法                               | 涵蓋套件管理器下載？                                 |
| ---------------------------------- | ---------------------------------------------------- |
| 專案 `.npmrc` 的 `registry=`       | ❌ **否**                                            |
| 全域 `~/.npmrc` 的 `registry=`     | ✅ 是                                                |
| `npm_config_registry` 環境變數     | ✅ 是                                                |
| `devEngines.packageManager.onFail` | ❌ **否**（`error` 與 `ignore` 都照樣下載且 exit 0） |

第一列最危險：專案相依確實會走內部 mirror，於是全隊都相信封閉網路沒問題 ——
但 `vp` 的第一步仍在往公網連，要到真的斷網那天才會發現。

完整說明與驗收方式：`vpr airgap`。

## 為什麼不用 YAML 函式庫

這支工具存在的目的就是列出這個 repo 拉了什麼進來。為了盤點供應鏈而先新增一個
第三方相依，是自己打自己的臉。需要的欄位只有五個，格式由 pnpm 的序列化器產生、
極度規律，值得手寫。

代價是要自己處理那個陷阱：**`pnpm-lock.yaml` 是兩份 YAML 文件**。
第一版用 `indexOf("packages:")` 找區段，只讀到第一份，回報「本專案有 19 個套件」——
少算 96%，而且輸出看起來完全正常。見 `DECISIONS.md` 的 C26。
