# @org/promise-check

**`specs/` 寫的框架承諾，現在還是真的嗎**（[`TESTING.md`](../../TESTING.md) 層 3 · 框架承諾）。

`HANDOFF.md`〈v1.0.0 承諾什麼〉列了五條承諾，每一條底下有一張「守它的／守什麼」表。
在這支工具之前，**那張表與實際跑的閘門對不對得上，只有人讀得出來** ——
那份文件自己招認過這件事。

⚠️ **`specs/` 底下不是每一份都是那五條之一。** 檔名走 `promise-N-` 的才是；
`gate-thresholds.feature`（C163）守的是量那些能力的尺會不會過期，
與 `tools/doc-facts` 同一類。這支工具對兩者一視同仁 —— 它問的是
「寫下來的還成不成立」，不是「這條算不算 v1 承諾」。

## 用法

```bash
node tools/promise-check/src/cli.ts
```

它接在 `scripts.gate`（也就是 `vpr gate`）與 Tier 2 上。

## 它做什麼

讀 `specs/*.feature`，對每一個場景：

1. 把版控裡的兩片切片、`platform`、`apps`、`.github` 與根層的 `vite.config.ts`
   **複製**到暫存目錄
2. 照「假設」那一句把副本弄壞
3. 跑「當」那一句指名的閘門
4. 比對「那麼」說的結果與訊息片段

⚠️ **repo 的原始碼一個位元組都不會被動到** —— 破壞發生在副本上。

### 沙盒契約（C127 §二）

副本裡有哪幾層是一份**契約**，不是最佳化：少一層的症狀不是「那一層沒被檢查」，
是被指名的閘門在那裡**噴 ENOENT 或安靜地掃到 0 個檔**，而 0 個檔在每一條
「必須紅」上長成〈承諾沒有牙齒〉、在對照組上長成綠燈。

| 層               | 誰在副本上讀它                                                   |
| ---------------- | ---------------------------------------------------------------- |
| `features`       | `conformance` 的切片契約（只放固定的兩片，理由見 `breakage.ts`） |
| `platform`       | `theme-verify` 的元件與代幣；`conformance` 的 CSP 與幽靈依賴     |
| `apps`           | 同上                                                             |
| `.github`        | `conformance` 的 `checkActionPinning`                            |
| `vite.config.ts` | `threshold-check` 被驗的對象 —— 那幾格門檻的數字（C163）         |

⚠️ **`tools/` 刻意不在裡面** —— 閘門自己的素材（`theme-verify` 的 `fixtures/`）
不隨 `--root` 走。⚠️ **複製走 `git ls-files`**，所以切分支留下的殘骸不會被
數進副本。守這份契約的是 [`tests/sandbox.test.ts`](tests/sandbox.test.ts)：
它逐層比對副本與真樹的檔數，而且每一條都是差分（改副本 → 數字要跟著動）。

## 規格是唯一來源，不是閘門行為的說明書

說明書會與閘門分岔，而分岔的那天沒有人會知道（`SCOPE.md` 開頭警告的正是這個，
`v1.0.3` 付過代價）。這裡的規格**被執行**，所以它分岔不了：

| 改壞規格的方式                 | 會怎樣           |
| ------------------------------ | ---------------- |
| 「必須紅」改成「必須綠」       | 承諾誤擋         |
| 訊息片段改成不會出現的字       | 紅在別的地方     |
| 「假設」那一句改寫             | 沒有接線 ＋ 孤兒 |
| 整個場景刪掉                   | 孤兒接線         |
| 規格檔改名或刪掉               | 規格不見了       |
| 承諾綁到沒接在 `gate` 上的閘門 | 閘門沒有接上     |
| 承諾綁到看不見副本的閘門       | 閘門指不到副本   |

⚠️ **倒數第二列是這支工具買到的東西裡最實在的一塊。** 一道閘門存在、跑得動，
不代表它會被執行 —— `tools/spec-report` 就是現成的反例（它接在 `vpr ready`
的最後一步，不在閘門鏈上）。

⚠️ **而最後一列擋的是比那更安靜的一種**（C124）：閘門存在、被執行、卻
**看不見那份副本**，於是每一次「照規格弄壞副本」之後跑的都是**沒有被弄壞的
真樹**。所以執行之前先探一次：指向一個空目錄與指向 repo 自己，輸出逐字相同
就是它沒看。

⚠️ **有兩種形狀，而兩種的處置一樣。** 舊的那種是**靜默忽略**不認得的旗標
（C123 §一 量到的病，C126 之後八支 CLI 都不再這樣）；今天的那種是閘門接了
`parseFlags` 但**沒有宣告 `--root`**，於是它**拒絕**了那個旗標 —— 兩趟都失敗、
訊息相同，探針判定一樣是「看不見」。⚠️ **哪一支是哪一種，不在這裡維護一份清單** ——
`probeRootSupport` 每次跑都會當場說，而寫在散文裡的那種數字沒有任何東西在守。
今天讀 `--root` 的是 `conformance`、`theme-verify`（C127）與 `threshold-check`（C163）。
⚠️ 對照組接不住這個方向 —— 那道保險守的是「沙盒建壞掉」（每一條該紅的都紅），
這裡是「閘門沒看沙盒」（每一條該綠的都綠）。

## 怎麼加一條承諾

**先寫規格，再補接線。** 反過來做的話，接線表會長出沒有承諾支撐的破壞手法，
而那是紅燈（孤兒）。

1. 在 `specs/*.feature` 寫下承諾，三句：`假設` / `當 跑 tools/<閘門>` /
   `那麼 它必須紅，訊息裡要出現 "片段"`
2. 在 [`src/breakage.ts`](src/breakage.ts) 補一段破壞手法，鍵與「假設」那一句
   **逐字相同**

⚠️ **每一份規格都要有一條期待綠燈的對照組**（「沒有人違規時不得說話」），
而且它先跑。沙盒建壞掉的話，每一條「必須紅」都會成功變紅，而原因是環境壞了。

## 它與 `tools/spec-report` 不是同一件事

|      | 這一支                 | `spec-report`                |
| ---- | ---------------------- | ---------------------------- |
| 讀   | `specs/*.feature`      | `features/*/specs/*.feature` |
| 誰寫 | 上游維護者             | **專案組自己**               |
| 問   | 腳手架的承諾還成不成立 | 業務功能完成幾條             |
| 產出 | 結束碼（它是閘門）     | `SPEC-REPORT.md`（它是報表） |

⚠️ 兩邊路徑刻意不重疊：混在一起的話，框架承諾會被算進那份拿去對外報進度的
完成率報表。這條分界由 `tests/cli.test.ts` 守著，不靠人記得。

## 開發

```bash
vp run @org/promise-check#test
```

反向測試在 [`tests/negative.test.ts`](tests/negative.test.ts) —— **兩個方向都驗**：
承諾說謊會紅，規格沒被讀到也會紅。第二個方向才是重點（見該檔檔頭）。

探針自己的測試在 [`tests/probe.test.ts`](tests/probe.test.ts)。⚠️ 它帶一支
**故意忽略 `--root` 的假閘門**（`tests/fixtures/ignores-root/`），理由是今天
唯一被規格指名的閘門真的讀 `--root` —— 探針寫出來就全綠，而全綠與「探針沒有
作用」長得一模一樣。那支假閘門是表裡唯一的非零列。
