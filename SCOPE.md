# 這棵樹上有什麼 —— 而每一項都有人寫過一句它是什麼

> 這份文件是**登記表，不是准入清單**。它回答一個問題：
> **版控裡的每一個目錄與根層檔，有沒有人寫過一句它是什麼。**
>
> ⚠️ **它不回答「准不准」。** 判準曾經帶著准入後果（「送 `main`」），而兩條線
> 併回一條之後那個後果消失了 —— 經過見 DECISIONS.md 的 **C136**。
> 一列填好了**不代表**那東西「可以」在這裡，只代表**有人判斷過**。
>
> 要用這個腳手架開案子的團隊，你主要要的是 [HANDOFF.md](HANDOFF.md)。
>
> ⚠️ **但你在 `platform/` 底下加目錄、或在根層加東西的時候會被送到這裡** ——
> `scope-check` 要求版控裡的每一個目錄與根層檔都在下面那兩張表登記一列。
> 那時候**那幾欄寫你們自己的理由就好**：這道閘門要的是「有人判斷過」。
>
> ⚠️ **`tools/` 底下不在這裡** —— 那一層改由 `tools/gate-roster` 登記
> （C136 §四），而它一樣會擋你、一樣要你寫一句理由。理由見下面那一節。

## 三份清單，三條軸 —— 刻意不互相抄

| 文件                             | 軸         | 它回答的問題                                     |
| -------------------------------- | ---------- | ------------------------------------------------ |
| HANDOFF〈v1.0.0 **不**涵蓋什麼〉 | **能力**   | 「我的案子要無障礙／SBOM，該用哪條分支？」       |
| 本檔                             | **目錄**   | 「這個目錄／根層檔，有沒有人寫過一句它是什麼？」 |
| [TESTING.md](TESTING.md)         | **正確性** | 「這個腳手架的對，是靠哪幾層守的？」             |

⚠️ **三邊不重述對方的內容，只互相指過去。** 同一件事抄成兩份、而沒有東西
斷言它們一致 —— 那正是 `v1.0.3` 才剛付過代價的病（HANDOFF〈已知的誠實缺口〉
第五條）。加一份清單而不加守它的機制，是在製造第五份手抄本。

## 判準的問法還在，而它**不決定准入**

- **面向交付物（含文件）→** 受益者是**拉 v1 去做案子的團隊**。
- **面向開發流程 →** 受益者是維護者。

問法是：**「這東西紅了，是誰的問題被擋下來？」** 這條線怎麼定出來的、以及
它為什麼不是「不服務五條承諾就出局」，見 DECISIONS.md 的 C72。

⚠️ **但它已經不帶後果了。** 原本寫在這裡的是「寫不出『受益者是拉 v1 的團隊』
那一句就不准進，送 `main`」—— 兩條線併回一條之後，「送 `main`」＝「留在原地」，
那個後果消失了（C134、**C136 §三**）。**現在它只分類，不判准入。**

⚠️ **所以不要拿它論證誰可以留在樹上、誰該被刪。** 下面那幾張表問的是
「有沒有人寫過一句」，不是「准不准」—— 而**沒有被治理不等於准許進入**（C93）。

## 事實來源是 **git**，不是工作樹

```bash
git ls-files -- platform/          # 這是 tools/scope-check 用的那一條
```

⚠️ **不要用 `ls`。** 切換分支不會刪掉被 ignore 的殘留目錄：`release/v1` 上
`ls tools/` 會列出一堆早已不在版控裡的目錄（移除之後 `node_modules`
還留在磁碟上）。用 `ls` 寫的檢查會把那些殘骸當成違規，而報告出來的東西
一個字都不對。

⚠️ **也不是 `git ls-tree HEAD`。** 那答的是「上一個 commit 裡有什麼」——
新增一支工具、`git add` 了、跑 `vpr ready`，**是綠的**，要等 commit 完才紅。
`ls-files` 讀的是 index，staged 的新目錄當場就看得見。

## `tools/` —— 這一層由 `tools/gate-roster` 登記

⚠️ **這一節刻意不叫「准許存在的」，也刻意沒有表格。** 那不是省略 ——
`tools/*` 的登記由 [`tools/gate-roster`](tools/gate-roster) 負責，
而**這份文件不重抄它**（C136 §四）。

`gate-roster` 的 `GATES` 與 `UNGATED` 兩份清單合起來涵蓋**每一個 `tools/*`
workspace 成員**，`UNGATED` 的「為什麼它不是閘門」**必填**，而且有機制在守
（`tools/gate-roster/src/check.ts` 的①：漏一支就紅）。這裡再列一張表，
就是同一件事的第二份手抄本，**而兩道機制互不斷言** —— 漂移的時候兩邊都是綠的。
那正是本檔開頭〈三份清單，三條軸〉警告的病。

⚠️ **你在 `tools/` 底下加目錄一樣會被擋** —— 只是擋你的是 `gate-roster` 的
「工具沒登記」，訊息會叫你把它加進 `GATES`（要寫 tiers）或 `UNGATED`（要寫理由）。
**要寫一句理由這件事一個字沒變。**

⚠️ **`tools/` 這個目錄本身**仍然登記在〈根層 —— 准許存在的〉那一節 ——
「這個頂層目錄該不該存在」與「它底下有哪些東西」是兩個問題，兩層各答各的。

⚠️ **這一節從 `v1.0.5` 到 C136 之間是一張 11 列的表**，而那 11 列是已刪分支
`release/v1` 的快照。合併之後樹上有 19 支，於是這道閘門對著 8 支報「樹上有、
沒登記」—— 而那張表的第三欄要求「寫得出受益者是拉 v1 的團隊」，
**其中至少一支依 C72 明文寫不出來**（`gate-roster` 自己）。經過見 C136 §四。

## 這份文件由 `tools/scope-check` 守著（`v1.0.5` 起）

```bash
./node_modules/.bin/vpr scope-check
```

**兩個方向都會紅：**

| 情況                 | 為什麼要紅                                                                      |
| -------------------- | ------------------------------------------------------------------------------- |
| 版控裡有、上面沒列   | 樹上悄悄多了東西，而沒有人寫過一句它是什麼 —— 沒寫就是沒判斷過                  |
| 上面列了、版控裡沒有 | **清單在說謊** —— README 的目錄樹曾經列著 `tools/sast/`，而那個目錄從來沒存在過 |

它比對的是 **`git ls-files`**，不是磁碟上的目錄。理由見 `tools/scope-check/src/tree.ts`：
切分支會留下含 `node_modules` 殘骸的空目錄，用磁碟當事實來源的檢查**會在開發機紅、
在 CI 綠**。找不到 git 時它直接失敗，**刻意不退回去掃磁碟** —— 一道「找不到就換個
寬鬆判準」的閘門，會在最需要它的環境裡安靜地變成另一件事。

⚠️ **這份文件刻意一個導出的數字都沒有**（全部列名字，不寫「幾支」）。
守哪幾份由 `tools/doc-facts` 的 `GUARDED` 決定，**這裡不重抄那份清單** ——
所以這份文件不進 `GUARDED`，而是寫成「就算沒有守衛也不會腐爛成假數字」的形狀。

⚠️ **這裡原本寫著「`GUARDED` 只有 `README` 與 `HANDOFF` 兩份」，而那句話
自己預言了它怎麼死**（「加第三份的那一刻……會同時變成假的」）。第三份是
`UI-SURVEY.md`，加在 `main` 上 —— 而這份文件當時在 `release/v1`，那裡沒有
那個檔案。**同一句話在兩條線上一真一假**，併線把它變成假的，而沒有任何東西
說話。經過見 **C136 §七**。

⚠️ **它守的是「有沒有寫」，不是「寫得對不對」。** 兩張表都驗每一列**第一格之後
沒有空格子**。填了什麼字機器讀不出來 —— 那仍然只有人能判斷。這道閘門保證的是
**沒有人可以跳過那幾格**（`v1.0.5` 起就這樣宣稱，而**到 C94 才真的做到**，見下）。

⚠️ **兩張表的紅燈訊息不一樣，因為兩張表的形狀不一樣。** `platform/` 是
「路徑／是什麼」，根層是「名字／這是什麼」。用同一句訊息會對著其中一層要求
一個**文件自己說不該存在**的欄位，而下一個人只會照著補。

⚠️ **而兩張表的訊息都不再要求「受益者是拉 v1 的團隊」那一句，也不再叫人
送 `main`**（C136 §五）—— 那個要求沒有後果了，留著只會讓 fork 了 v1 的團隊
去寫一句他們依定義寫不出來的話，或去找一條不存在的分支。
訊息改成一句，並且明說：**它綠了不代表那東西「可以」在這裡。**

⚠️ **`v1.0.5` 到 C94 之間，上面那句保證是假的。** `parse.ts` 只捕捉第一格，
所以把某一列後面幾欄清空，解析照樣收下、閘門照樣綠（實測：清空 `doc-facts`
那一列，`listed` 還是 8 項）。**文件宣稱了一個保證，而程式碼沒有交付它** ——
跟 README 曾經列著從來不存在的 `tools/sast/` 是同一種病，方向相反。

C94 修的是**程式碼**，不是收回那句話：`#66` 的紅燈訊息整段建立在「你得寫出
那一句」之上，把保證拿掉等於把 `#66` 的前提抽掉。⚠️ 而它買到的仍然只有
「跳過要動手寫一個字」—— 填 `x` 過得了。**那不是這道閘門的漏洞，是它的邊界。**

### 先文件、後檢查的順序是刻意的

`v1.0.4` 先用人工把判準跑一遍，`v1.0.5` 才寫檢查。反過來做，補文件的動機會變成
「讓閘門轉綠」而不是「把判準真的跑一遍」—— 而人工那一遍掉出了兩件事：
`doc-facts` 的歸屬問題（見上面那格），以及 README 目錄樹裡那個從來不存在的
`tools/sast/`。
